# Сандуновские бани — фронтенд

Angular 21 (standalone-компоненты, сигналы, `rxResource`), TypeScript `strict`, SCSS. Дизайн перенесён из макета «Сандуновские бани — макет сайта»: цвета, шрифты (Cormorant Garamond + Inter) и компоненты UI-кита — в `src/styles.scss`. UI-библиотеки не используются: у макета своя визуальная система, Material/PrimeNG пришлось бы перекрашивать целиком.

## Структура

- `src/app/pages/<экран>/` и `src/app/admin/<экран>/` — страницы, у каждой `.ts` + `.html` + `.scss`.
- `src/app/shared/` — мелкие общие компоненты (шапка, подвал, сообщения, иконки) с inline-шаблонами.
- `src/app/core/` — модели, API-слой (`api/http-booking-api.ts` — бекенд, `api/demo-booking-api.ts` — демо, `api/wire.ts` — типы ответов API), хранилище оформления, авторизация.
- `src/environments/` — адрес API и выбор источника данных.
- `src/styles.scss` — дизайн-токены, базовые компоненты UI-кита и общие утилиты раскладки (`.stack`, `.cluster`, `.spread` и т. п.).

## Запуск

```bash
npm install
npm start          # http://localhost:4200
npm run build      # production-сборка в dist/
```

Нужен Node.js ≥ 20.19 (проверено на 24.11).

## Бекенд

Фронтенд работает с бекендом MVP из `backend/` (контракт — `backend/api/openapi.yaml`, памятка — `backend/FRONTEND_GUIDE.md`) через `HttpBookingApi` (`src/app/core/api/http-booking-api.ts`). Страницы знают только абстрактный `BookingApi` и модели `models.ts`: адаптер переводит ответы API в эти модели.

Локальный запуск:

```bash
cd backend
python3 scripts/init-env.py
docker compose build catalog booking payment identity
docker compose up -d --no-build --wait
cd ../frontend
npm start
```

- Dev-сервер проксирует `/api` на шлюз `http://localhost:8080` (`proxy.conf.json`), поэтому `ALLOWED_ORIGIN` бекенда и порт фронтенда не важны. После изменения `proxy.conf.json` или `angular.json` dev-сервер нужно перезапустить.
- Рабочая сборка ходит на относительный `/api/v1` — фронтенд и API должны быть за одним шлюзом. Иначе укажите адрес в `src/environments/environment.ts` и разрешите origin в `ALLOWED_ORIGIN` бекенда.
- Демо-данные без сервера: `api: 'demo'` в `src/environments/environment.development.ts`.
- Вход в админку: `ADMIN_USERNAME` / `ADMIN_PASSWORD` из локального `backend/.env` (файл не коммитится).

Что важно знать про связку:

- Возраст каждого ребёнка указывается при оформлении: от него сервер определяет место и тариф. Возрастные границы во фронтенде не захардкожены — ошибки состава гостей приходят из расчёта.
- «Перейти к оплате» = `POST /orders` (ключ повтора на одно и то же содержимое) + `POST /orders/{id}/hold`. Таймер считается по `expires_at` с поправкой на `server_time`.
- Отказ тестовой оплаты не снимает удержание: можно повторить до конца срока, каждая попытка — с новым ключом. «Ответ потерян» — платёж отправляется, а ответ намеренно игнорируется; итог восстанавливается по заказу.
- Схема зала рисуется по координатам сервера (0–1000); на узком экране — списком мест.
- Админка: расписание — исключения на дату поверх недельного шаблона, тарифы публикуются набором с версией (новое правило разрезает действующие по периоду и дням), блокировки — на интервал сеанса.

## Личный кабинет

**В бекенде MVP кабинета нет** (вход по SMS не реализован), поэтому с `HttpBookingApi` он скрыт: нет кнопки в шапке, маршруты `/cabinet*` ведут на главную. Работает только в демо-режиме.

Добавлен по макету и **выходит за рамки ТЗ v0.2**: там аккаунт не обязателен, а телефон без подтверждения не открывает историю заказов. Поэтому:

- кабинет необязательный, покупка без входа работает как раньше;
- вход только по подтверждённому номеру: одноразовый код из SMS (в демо-режиме код показывается на экране);
- в кабинете видны оплаченные заказы, оформленные из кабинета или на этот номер;
- при оформлении заказа имя и телефон подставляются из профиля.

Срок хранения данных, смена номера, текст согласия и восстановление доступа нужно согласовать с заказчиком и описать в ФЗ. Серверная часть (отправка SMS, лимиты попыток, сессии) — за бекендом.

В демо-режиме для входа подходит тестовый номер `+7 900 000-00-00`: у него уже есть билеты на сегодня, предстоящие посещения и история.

## Что остаётся «на согласовании» (по ТЗ/ФЗ)

Формат телефона, базовое число гостей и вместимость саун (в тестовых данных бекенда — допущение), праздничные и льготные тарифы. Возрастные границы, шаг и перерыв саун, срок ссылки на билет, вход администратора и повторная оплата после отказа теперь определяет бекенд MVP (`backend/MVP_DECISIONS.md`). В интерфейсе такие места помечены как «на согласовании» или «[уточняется]» и не заменены выдуманными значениями. Исключение — демо-цены, без которых нельзя показать расчёт.
