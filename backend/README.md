# Backend MVP «Сандуновские бани»

Go backend для выбора посещения двух бань: места на фиксированный сеанс или сауна целиком, полный расчёт стоимости, удержание ресурсов на 10 минут, тестовая оплата и защищённый электронный билет. Администратор создаёт и архивирует бани/отделения, управляет ресурсами, расписаниями, тарифами и блокировками; владелец управляет сотрудниками. Есть календарь, редактирование черновика, истории и PDF-билет. Начальный каталог содержит две бани, новые можно создавать через API.

Объём определён ТЗ/ФЗ от 08.11.2026. Принятые трактовки и допущения перечислены в [MVP_DECISIONS.md](MVP_DECISIONS.md). Настоящие списания, фискализация и фактический допуск посетителей в этот MVP не входят. Максимальная вместимость саун в тестовом каталоге — синтетическое значение 10; тарифная база отдельно равна 5 или 6.

Для подключения фронтенда: [памятка фронтенд-разработчика](FRONTEND_GUIDE.md) — локальный запуск, Swagger, CORS, авторизация и сценарий оформления.

## Быстрый локальный запуск

Нужны Docker Engine с Compose v2.24+ и Python 3 для однократного создания конфигурации. Рекомендуется выделить Docker не менее 4 ГБ памяти. Все команды выполняются **из `backend/`**:

```bash
python3 scripts/init-env.py
docker compose build catalog booking payment identity
docker compose up -d --no-build --wait
```

Сборка компилирует сервисы последовательно в одном общем этапе с ограниченным параллелизмом Go. Если `.env` уже существует, генератор его не изменяет. В `.env` записываются случайные пароли и ключи; файл имеет права `0600`, исключён из Git и сборочного контекста.

- API: <http://localhost:8080/api/v1/baths>
- Swagger UI: <http://localhost:8080/swagger/>
- OpenAPI: <http://localhost:8080/openapi.yaml>
- Проверка proxy: <http://localhost:8080/healthz>

Учётные данные администратора находятся в локальном `.env`: `ADMIN_USERNAME` и `ADMIN_PASSWORD`. Не пересылайте этот файл и не вставляйте его целиком в логи.

Миграции запускаются одноразовыми контейнерами до старта сервисов. При успешном запуске эти четыре контейнера и `kafka-init` имеют состояние `Exited (0)` — это штатное состояние. Основные контейнеры остаются запущены.

```bash
docker compose ps -a
docker compose logs --tail=100 booking payment
docker compose stop
docker compose up -d --no-build --wait
```

Обычные остановка и перезапуск сохраняют данные в томах. Команда `down -v` удаляет данные; она не требуется для запуска и обновления.

## Стек и структура

Go 1.27.3, `net/http` и chi, pgx/v5, golang-migrate, Redis и go-redis/v9, Apache Kafka в режиме KRaft и kafka-go, JSON-логи slog, gopdf с встроенными шрифтами Liberation для кириллицы, OpenAPI 3.1 и Swagger UI. Точные версии библиотек закреплены в `go.mod`/`go.sum`, образы — в Compose и Dockerfile.

```text
backend/
  services/
    catalog/       # каталог; собственная БД и миграции
    booking/       # расписание, тарифы, ресурсы, заказы, билеты
    payment/       # попытки тестовой оплаты
    identity/      # администраторы и сессии
  internal/platform/   # HTTP, конфигурация, клиенты и транспорт событий
  cmd/migrate/         # применение миграций
  cmd/replay/          # явный повтор сообщений из DLQ
  api/openapi.yaml
  deploy/              # proxy, PostgreSQL, TLS, резервное копирование
  seed/catalog.json    # исходные номера и нормализованные координаты мест
  tests/integration/
  docs/
```

Внутри сервиса HTTP-обработчики вызывают бизнес-правила и слой хранения. Между сервисами используются HTTP и Kafka. Каждая БД доступна отдельной роли PostgreSQL. Сервисы не читают чужие таблицы. Контейнеры Go работают от пользователя `10001`, с файловой системой только для чтения и без Linux capabilities.

Готовые схемы содержат **149 явно пронумерованных мест**: Баня №1 — 32 мужских общих, 32 женских общих, 18 мужских «Купель», 18 женских «Купель»; Баня №2 — 25 мужских и 24 женских. Использована нумерация с предоставленных изображений, включая номера 111 и 112 и отсутствие 101–110 в женской «Купели». Координаты нормализованы в поле 1000×1000; это ориентиры для клиента, не конструктор геометрии. Сводные вместимости опросного листа не заменяют номера на схемах.

Минимальная длительность, шаг начала, шаг длительности и санитарный перерыв хранятся в PostgreSQL для каждого онлайн-отделения и возвращаются в `booking-config`. В MVP для саун это 60, 30, 60 и 30 минут соответственно; для сеансов санитарные промежутки определены самим расписанием. Справочные отделения содержат предоставленные графики и тарифы в описании и не предлагают онлайн-оформление.

## Конфигурация

| Переменная | Назначение |
| --- | --- |
| `APP_ENV` | `development` или `production` |
| `PUBLIC_URL` | Внешний адрес API; используется в билетной ссылке |
| `ALLOWED_ORIGIN` | Один разрешённый origin для CORS, без wildcard |
| `COOKIE_SECURE` | Для сервера с HTTPS обязательно `true` |
| `HTTP_PORT` | Локальный порт proxy, по умолчанию 8080 |
| `DOMAIN` | Домен для Caddy и автоматического HTTPS |
| `POSTGRES_PASSWORD` | Пароль административной роли БД для инициализации/бэкапов |
| `CATALOG_DB_PASSWORD`, `BOOKING_DB_PASSWORD`, `PAYMENT_DB_PASSWORD`, `IDENTITY_DB_PASSWORD` | Отдельные пароли сервисных БД |
| `REDIS_PASSWORD` | Пароль Redis |
| `INTERNAL_API_KEY` | Общий ключ внутренних HTTP-вызовов, минимум 32 символа |
| `ORDER_TOKEN_KEY`, `TICKET_TOKEN_KEY` | Разные ключи производных секретных токенов заказов и билетов, минимум 32 символа |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | Создание первоначального администратора; пароль 12–72 байта |
| `BACKUP_DIR` | Каталог для бэкапов; для сервера — отдельное защищённое хранилище |

Compose формирует для сервисов `DATABASE_URL`, `REDIS_URL`, `KAFKA_ADDR`, `KAFKA_TOPIC`, `IDENTITY_URL`, `BOOKING_URL`, `PAYMENT_URL`, `CATALOG_URL` и `HTTP_ADDR`. При запуске Go-процесса отдельно эти переменные нужно задать самостоятельно. На сервере БД и брокер остаются внутри контейнерной сети.

Пароль администратора создаётся только при отсутствии записи. Изменение `ADMIN_PASSWORD` при существующей БД не обновляет её пароль. Изменение паролей БД в `.env` также не меняет существующие роли PostgreSQL; ротация должна сопровождаться обновлением ролей. Смена ключей токенов нарушает восстановление ранее выданных ссылок: сохраняйте их вместе с резервной копией конфигурации.

## API и пример оформления

Полный контракт, ошибки, ограничения полей и способы авторизации находятся в [OpenAPI](api/openapi.yaml). Для практического воспроизведения всего пути используйте:

```bash
python3 scripts/demo.py
```

Скрипт найдёт ближайший опубликованный сеанс, создаст синтетический заказ, удержит место, выполнит тестовый успех через Kafka и сохранит результат в `tmp/demo-result.json` с правами `0600`. Он не печатает секретные токены. Данные этого заказа останутся в локальной БД.

Основные запросы:

```bash
curl -s http://localhost:8080/api/v1/baths
curl -s http://localhost:8080/api/v1/baths/1/departments
curl -s http://localhost:8080/api/v1/departments/b1-male-general/resources
curl -s 'http://localhost:8080/api/v1/departments/b1-male-general/availability?date=2026-11-11'
```

Дата в примере должна находиться в текущем окне продажи. Даты и время передаются в RFC3339 с часовым поясом; календарные правила применяются в `Asia/Yekaterinburg`. Суммы передаются в целых копейках RUB.

Порядок HTTP-вызовов:

1. `POST /api/v1/quotes` с выбором отделения, ресурсов, начала/окончания и категорий/количеств гостей и детского возраста по тарифу — предварительная цена без резерва.
2. `POST /api/v1/orders` с `selection`, `buyer` и случайным UUID v4 в `X-Idempotency-Key` — черновик и `order_token`.
3. `POST /api/v1/orders/{id}/hold`, тело `{}`, `Authorization: Bearer <order_token>` — атомарное удержание и окончательная цена. Проверьте `price_changed`.
4. `POST /api/v1/orders/{id}/payments` с новым `X-Idempotency-Key`, тем же bearer-токеном и телом:

```json
{
  "amount_kopecks": 45000,
  "currency": "RUB",
  "price_hash": "значение из ответа hold",
  "outcome": "success"
}
```

Значение суммы в примере заменяется фактической суммой удержания. `outcome` бывает `success` или `declined`. Ответ `202` со статусом `pending` означает сохранённую попытку, результат которой ещё обрабатывается. Опрашивайте `GET /api/v1/orders/{id}/payments/{paymentID}` и `GET /api/v1/orders/{id}`. После `confirmed` в заказе доступен `ticket_url`.

Токен заказа даёт доступ только к одному заказу. Билетный токен разрешает только чтение одного подтверждённого билета, без контактов покупателя; срок — 30 дней после окончания посещения. Доставка по email/SMS и восстановление потерянной ссылки через оператора не входят в MVP. Сохраняйте секретный ключ создания заказа, чтобы безопасно повторить исходный запрос при потере первого ответа.

Администратор входит через `POST /api/v1/admin/sessions`. Для Swagger удобно передать полученный `access_token` в схему `adminBearer`. Поддерживается также HttpOnly cookie; изменяющие запросы с cookie требуют `X-CSRF-Token` из ответа входа. Сессия действует 8 часов, выход отзывает её немедленно.

## PostgreSQL и конкурентность

У каждого сервиса каталог миграций `services/<name>/migrations`. Инструмент хранит версию и признак незавершённой миграции в `schema_migrations`. Повторное применение не изменяет уже применённые миграции.

```bash
docker compose run --rm migrate-booking up
docker compose run --rm migrate-catalog up
docker compose run --rm migrate-payment up
docker compose run --rm migrate-identity up
```

`down` откатывает одну последнюю миграцию и предназначен для отдельной тестовой БД. Перед изменениями рабочего окружения создайте резервную копию. Применённые файлы не редактируются; для новых изменений добавляются следующие номера миграций.

Бронирование, оплата, освобождение и административные изменения получают блокировку отделения, затем заказа в одном порядке. Это обеспечивает сериализацию и исключает взаимную инверсию блокировок. PostgreSQL дополнительно запрещает пересекающиеся активные интервалы одного ресурса exclusion constraint на `tstzrange` с `btree_gist`.

Действительность удержания проверяется по часам БД после блокировок: `now < expires_at`. При равенстве срок истёк. Очиститель работает раз в 2 секунды, но новый заказ не зависит от его своевременности: истёкшие удержания освобождаются также в транзакции нового действия. Ресурсы группы удерживаются и освобождаются целиком. Обновление страницы, повтор запроса и отказ оплаты не продлевают срок.

Успешное подтверждение оплаты и право на билет фиксируются одной транзакцией booking-service. Изменение тарифа не переписывает снимок удержанной цены. Расписания, тарифы и блокировки защищены версиями; устаревшее сохранение получает `409`. Изменения сотрудников записываются в журнал аудита.

## Redis и Kafka

Каталог кэшируется на 60 секунд, опубликованные настройки бронирования — на 30 секунд. После административного изменения настройки удаляются из кэша напрямую и через событие. Важные проверки оформления читают PostgreSQL. Ошибка Redis допускает чтение справочника из БД; вход администратора при недоступном ограничителе запросов возвращает `503`.

Топик `banya.events.v1` содержит версионированные события с ключом агрегата. Группы `booking.v1`, `payment.v1` и `catalog.v1` имеют независимые позиции. Метаданные отделений передаются событиями `catalog.department.updated`, booking подтверждает `booking.catalog_applied`. Основные события: `order.held`, `order.released`, `order.expired`, `order.confirmed`, `payment.result`, `booking.payment_processed`, `department.changed`, `resource.blocked`, `resource.unblocked`. Формат сообщений задан в [схеме событий](api/events.v1.schema.json); порядок доставки и повторов описан ниже.

Каждый producer сохраняет outbox в одной транзакции с бизнес-изменением. Публикация использует подтверждение всех доступных ISR; при ошибке запись остаётся для повтора с увеличивающейся задержкой до 64 секунд. Доставка — как минимум один раз. Inbox и уникальные идентификаторы платёжных решений предотвращают повторный эффект.

После пяти неудачных обработок consumer сохраняет исходное сообщение в `banya.events.v1.dlq` с заголовком `failed_group`; позиция исходного сообщения подтверждается только после успешной записи DLQ. Исправив причину, выполните явный повтор:

```bash
docker compose exec booking /app/replay -broker kafka:9092 -group booking.v1 -limit 1
```

Для групп `payment.v1` и `catalog.v1` укажите соответствующее имя. Не создавайте новые идентификаторы при повторе: прежние обеспечивают идемпотентность. Пока Kafka недоступна, платёж может оставаться `pending`; отсутствие ответа не считается успехом или отказом. Поздняя доставка после срока удержания отклоняется и не занимает ресурс заново.

## Проверки

Go-команды выполняются из `backend/`:

```bash
go build ./...
go test ./...
go vet ./...
go test -race ./services/booking/internal ./internal/platform
```

Обычный `go test ./...` запускает unit-тесты; интеграционные тесты явно пропускаются без флага. Для настоящих PostgreSQL, Redis, Kafka и HTTP API:

```bash
docker compose -f docker-compose.yml -f compose.local.yaml up -d --no-build --wait
BANYA_INTEGRATION=1 go test -count=1 -v ./tests/integration
```

`compose.local.yaml` открывает на loopback PostgreSQL `55432`, Redis `56379`, Kafka `19092`. Не подключайте этот файл на сервере. Тесты требуют `APP_ENV=development`, используют синтетические контакты и собственные идентификаторы, не очищают таблицы и не удаляют существующие заказы. Они оставляют оплаченные тестовые заказы, аудит и изменённую на 1 рубль тестовую цену отделения.

Интеграционные сценарии: каталог и настоящая нумерация, чужой доступ, восстановление создания, конкурентная группа, конфликт одного места, истечение, поздний успех, отказ и повтор оплаты, частичная сумма, билет, повторная доставка Kafka, интервалы/перерыв сауны, сохранение цены, административные версии и блокировки. Фактический протокол проверок находится в [docs/verification.md](docs/verification.md).

Дополнительно проверяются публикация расписания, cookie/CSRF, гонка освобождения с оплатой и перенос неверных событий в DLQ. Для воспроизводимых отказов зависимостей в локальном окружении: `python3 scripts/test-outages.py redis` или `python3 scripts/test-outages.py kafka`. Скрипты кратковременно останавливают соответствующий контейнер и восстанавливают его в `finally`; не запускайте их одновременно с другими интеграционными проверками.

## Серверное развёртывание

Подготовьте Linux-сервер с Docker/Compose, доменом и DNS-записью на него. Откройте 80/443; публичный доступ к PostgreSQL, Redis, Kafka и внутренним HTTP-портам не требуется. Скопируйте `backend/`, создайте отдельный серверный `.env` и задайте:

```dotenv
APP_ENV=production
DOMAIN=booking.example.ru
PUBLIC_URL=https://booking.example.ru
ALLOWED_ORIGIN=https://booking.example.ru
COOKIE_SECURE=true
BACKUP_DIR=/mnt/isolated-banya-backups
```

```bash
docker compose build catalog booking payment identity
docker compose -f docker-compose.yml -f compose.production.yaml --profile ops up -d --no-build --wait
```

Caddy получает и обновляет HTTPS-сертификат для домена. Локальный порт 8080 у proxy в серверной конфигурации снимается. Swagger доступен по `/swagger/` того же домена. Производственные секреты должны отличаться от локальных. Внешнее хранилище резервных копий и доступность DNS/сертификатов обеспечивает владелец серверной инфраструктуры.

Ежедневный backup-контейнер сохраняет четыре custom-format дампа PostgreSQL и удаляет только собственные файлы старше 30 дней. Для разовой копии:

```bash
docker compose --profile ops run --rm --no-deps backup once
```

Каждый такой дамп транзакционно согласован внутри своей БД. Онлайн-дампы разных БД не задают общую точку времени для межсервисного процесса. Для согласованной контрольной копии перед обновлением используйте `python3 scripts/backup-consistent.py`: скрипт останавливает записывающие сервисы, делает четыре дампа и возвращает только ранее работавшие сервисы. Это краткое плановое окно недоступности оформления. БД, брокер и существующие тома не пересоздаются.

Проверка восстановления локальной копии без изменения БД приложения: `python3 scripts/test-restore.py`. Скрипт использует отдельные случайно названные базы и удаляет только созданные им тестовые базы. Для проверки миграций: `go build -o bin/migrate ./cmd/migrate`, затем `python3 scripts/test-migrations.py` при поднятом окружении с `compose.local.yaml`.

Восстановление сначала проверяется в отдельной пустой БД: `pg_restore --exit-on-error --no-owner -d <test_database> <dump>`. Для восстановления рабочего контура остановите изменяющие данные сервисы, подготовьте отдельные пустые БД нужных владельцев, восстановите дампы соответствующими сервисными ролями, верните сохранённые ключи и проверьте версии миграций, после чего переключайте сервисы на восстановленные БД. Восстановление поверх текущих пользовательских данных не выполняется автоматически.

Перед запуском восстановленных catalog/booking/payment в **восстановленных отдельных БД** сбросьте отметки доставки outbox:

```sql
UPDATE outbox SET delivered_at = NULL, next_attempt_at = clock_timestamp();
```

Так события с прежними ID повторно публикуются даже при утрате Kafka или истечении её семидневного хранения; восстановленный inbox защищает уже обработанные результаты от повторного применения. Не сбрасывайте inbox и не меняйте ID событий. Это действие требуется при восстановлении, а не при обычном перезапуске. Проверка `scripts/test-restore.py` проверяет и этот шаг на своих временных БД. Сохраните оригинальные ключи токенов и шифрования из защищённого окружения: без них прежние ссылки и зашифрованные ответы недоступны.


Для обновления сохраните резервную копию, соберите образы новой версии и выполните `up -d --no-build --wait`: миграционные контейнеры должны завершиться успешно. При неудачной миграции сервисы не запускаются; не сбрасывайте dirty-версию без анализа состояния БД.

Конфигурация рассчитана на один сервер и один брокер Kafka. Это воспроизводимый контур MVP без гарантии высокой доступности. Мониторинг может проверять `/healthz` proxy и `/readyz` каждого сервиса в закрытой сети; `/readyz` проверяет БД, а временная недоступность Kafka представлена сохраняющимися outbox/pending и логами. Логи не содержат request URI, bearer-токены, билетные ссылки или тела с контактами.


## Повторы запросов, контакты и дополнения API

Все публичные POST/PUT/PATCH, включая расчёт и вход администратора, требуют `X-Idempotency-Key` с UUID v4. Для новой операции — новый ключ; при потере ответа повторяются тот же URL, метод и точное тело с прежним ключом. Сохранённый ответ не продлевает резерв и может описывать прошлое состояние: текущее состояние получают GET. Обычные успешные ответы сохраняются на 24 часа, вход — на восемь часов; ключи создания и оплаты дополнительно защищены уникальностью записей. `409 idempotency_conflict` означает иное содержимое при прежнем ключе, `409 request_in_progress` — нужно повторить тот же запрос позже. Старый заголовок `Idempotency-Key` принимается как псевдоним; нельзя передать два разных значения.

Состав гостей:

```json
[{"category":"adult","count":2},{"category":"child","age":5,"count":1}]
```

Для взрослого точный возраст не нужен. Прежний ввод `age/count` совместим, но в ответе взрослые показаны категорией без возраста.

У неоплаченного заказа bearer-доступ и контакт действуют 24 часа с создания. После подтверждения — до 30 дней после конца посещения. После срока запрос владельца получает 404, администратор — заказ с `buyer: {}`. Очистка физически удаляет контакт и хеш разрешения при старте и далее раз в минуту; истёкшие ответы HTTP и сессии также удаляются. Проверка срока выполняется на каждом обращении независимо от очистителя. Дампы имеют собственный срок хранения 30 дней. Подробности и правила восстановления описаны в [MVP_DECISIONS.md](MVP_DECISIONS.md).

GET/PUT `/api/v1/admin/departments/{departmentID}/info` позволяют администратору менять описание любого отделения, включая часы и цены справочного режима. PUT принимает `{ "version": 1, "description": "..." }`, bearer/защищённую cookie и ключ повтора. Для онлайн-расчётов используются отдельные API расписаний и тарифов. Описание — простой текст, его нужно безопасно отображать без интерпретации как HTML.

```bash
python3 -m venv .venv-check
.venv-check/bin/pip install -r scripts/requirements-check.txt
.venv-check/bin/python scripts/validate-api.py
```

Результат без секретов записывается в `tmp/api-verification.json`. Скрипт проверяет все 65 операций текущей спецификации, включая `/healthz`. Отдельно Swagger UI и файл OpenAPI доступны по ссылкам из раздела запуска.


Административные GET списка и карточки заказа дополнительно возвращают `payment`: фактический статус последней попытки и подтверждения, `paid_kopecks`, валюту, признак теста и последнюю попытку с причиной отказа. `pending` не является оплатой; `paid_kopecks` равен полной сумме только при подтверждённом заказе. Платёжная сводка загружается из payment через закрытый HTTP API; его адрес задаёт `PAYMENT_URL` (в Compose `http://payment:8080`). Если сервис недоступен, административное чтение получает 503. Внутренний пакетный маршрут не публикуется в proxy.


## Расширенное администрирование

Полные тела запросов и ответы 65 операций находятся в Swagger. Согласованный объём и бизнес-решения: [MVP_DECISIONS.md, раздел 13](MVP_DECISIONS.md#13-расширение-api-пункты-1-и-2-и-администрирование-бань).

| Задача | Endpoints под `/api/v1` |
| --- | --- |
| Сотрудник | `GET /admin/me`, `PUT /admin/me/password` |
| Собственные сессии | `GET /admin/sessions`, `DELETE /admin/sessions/{sessionID}` |
| Сотрудники (owner) | `GET/POST /admin/employees`, `PATCH /admin/employees/{employeeID}` |
| Бани | `GET/POST /admin/baths`, `GET/PATCH /admin/baths/{bathID}` |
| Отделения | `GET/POST /admin/baths/{bathID}/departments`, `GET/PATCH /admin/departments/{departmentID}` |
| Ресурсы | `GET/POST /admin/departments/{departmentID}/resources`, `PATCH .../resources/{resourceID}` |
| Политика | `GET/PATCH /admin/departments/{departmentID}/booking-policy` |
| Предпросмотры | `POST /admin/departments/{departmentID}/schedule-preview`, `POST .../tariff-preview` |
| Правка блокировки | `PATCH /admin/resource-blocks/{blockID}` |
| Истории | `GET /admin/departments/{departmentID}/history`, `GET /admin/orders/{orderID}/history` |
| Попытки оплаты | `GET /orders/{orderID}/payments`, `GET /admin/orders/{orderID}/payments` |
| Публичная карточка | `GET /baths/{bathID}` |
| Календарь | `GET /departments/{departmentID}/availability-calendar?from=YYYY-MM-DD&to=YYYY-MM-DD` |
| Черновик | `PATCH /orders/{orderID}` с собственным bearer-токеном |
| PDF | `GET /tickets/{token}/pdf` по той же защищённой ссылке |

Первый сотрудник становится `owner`. Только владелец создаёт/блокирует сотрудников и меняет их роли. Последнего активного владельца нельзя заблокировать или понизить. `admin` имеет права хозяйственного администрирования. Смена своего пароля сохраняет текущую сессию и отзывает остальные; блокировка, сброс пароля и смена роли отзывают все сессии затронутого сотрудника.

Создание бани требует `name`, `address`; укажите `active: true`, чтобы сделать её публичной. Онлайн-отделение создаётся вместе с `booking_setup`: политика, расписание, тарифы, метки и координаты ресурсов. Сервер назначает ID. Для справочного `mode: info` конфигурация онлайн-продажи не передаётся. Режим и родитель существующего отделения неизменяемы. Сохранённая `booking_setup` — начальная конфигурация; актуальные настройки после изменений читайте из booking API.

Каталог владеет метаданными, booking — расчётом и ресурсами. Создание отделения и изменения с проекцией возвращают `202` и `sync_status: pending`; опрашивайте административную карточку до `ready`. `error` требует исправления или операторского повтора после устранения причины. При недоступной Kafka изменения сохраняются в outbox и остаются `pending`. Новое отделение появляется публично только после подтверждения настройки. Для бани без отделений PATCH возвращает `200`.

Архивирование — `PATCH` с актуальной `version` и `active: false`. Физического DELETE бань/отделений/ресурсов нет. Новые продажи блокируются после применения проекции (`ready`); уже удержанные/оплаченные заказы сохраняются, удержанный заказ разрешено оплатить до его срока. Цена, состав и реквизиты существующего билета остаются снимком покупки.

Для каждого PATCH передавайте `version` и минимум одно изменение, для создания ресурса — `scheme_version`. При 409 перечитайте актуальную версию. Конфликтующие с действующими оформлениями изменения политики, расписания и ресурсов отклоняются. Предпросмотры ничего не публикуют; для публикации используются прежние PUT расписания/тарифа с актуальной версией. Любой POST/PUT/PATCH требует нового UUIDv4 `X-Idempotency-Key`, безопасный повтор — прежнего ключа и неизменного тела.

Истории используют курсор: `limit=1..100`, затем одновременно `before=next_before` и `before_id=next_before_id`. Контакты в историю не копируются. Список попыток оплаты использует обычные `limit/offset`. Календарь принимает 1–31 день включительно и не резервирует ресурсы.

Дополнительная проверка отказа Kafka для нового каталога: `python3 scripts/test-catalog-recovery.py`. Она проверяет pending/скрытие, сохранённый retry, восстановление проекции и безопасный повтор. Синтетическая баня архивируется. Эти проверки, как и прочие outage-скрипты, запускайте отдельно от интеграционных тестов. Скрипт контрактов сохраняет тестовый PDF в `tmp/pdfs/ticket-verification.pdf`; для визуальной проверки доступен `pdftoppm`.

Пункт 3 прежнего расширения API (реальная оплата, отмены/возвраты/переносы и внешняя доставка/восстановление) остаётся за рамками согласованного этапа.


Контракт Kafka проверяется по реальным сохранённым конвертам всех трёх producers: `python scripts/validate-events.py` (в окружении Python с jsonschema, описанном выше). Этот скрипт только читает outbox и не изменяет позиции/доставку событий.


## Защита нагрузки и новые параметры списков

Публичный каталог, административные ресурсы/блокировки и собственные сессии принимают `limit=1..100` (по умолчанию 50), `offset=0..10000`. Для списка отделений `groups` содержит только текущую страницу. Блокировки дополнительно фильтруются по `active`, `from`, `until` (RFC3339, пересечение периода) и `resource_id`. Обновлённые ответы и PDF-статусы 206/304/416 описаны в Swagger.

По умолчанию разрешены 5 удержаний и 100 удержанных ресурсов на клиентский адрес. Частота запросов, пределы PDF и сроки транспортных данных настраиваются через переменные в `.env.example`; 429/503 требуют повтора с учётом Retry-After. Контейнеры имеют ограничение 256 MiB, Go — мягкий бюджет 192 MiB. Принятые ограничения описаны в [MVP_DECISIONS.md, раздел 14](MVP_DECISIONS.md#14-исправления-аудита-безопасности-и-памяти), правила мониторинга находятся в [deploy/monitoring/alerts.yml](deploy/monitoring/alerts.yml).

Дополнительные проверки из `backend/`:

```bash
go build -o bin/migrate ./cmd/migrate
python3 scripts/test-regressions.py
python3 scripts/test-governance.py
```

Первая использует отдельную временную БД и race detector, затем запускает PDF-бенчмарки без race. Вторая проверяет gateway/метрики/PDF с небольшой ограниченной конкуренцией. Они не заменяют нагрузочное испытание на целевом сервере.

Это один последовательный клиент, не нагрузочный тест и не доказательство отсутствия всех утечек.
