# Памятка для фронтенд-разработчика

## 1. Что представляет собой backend

Backend MVP «Сандуновские бани» позволяет выбрать места на сеанс или арендовать сауну целиком, рассчитать стоимость, оформить заказ, удержать ресурсы на 10 минут, выполнить тестовую оплату и получить билет. Для сотрудников есть административный API управления банями, отделениями, расписаниями, тарифами, заказами и доступами.

Начальные данные: две бани, 16 действующих отделений и схемы со 149 пронумерованными местами. Новые бани и отделения можно создавать через API.

Внутри работают четыре Go-сервиса: `catalog`, `booking`, `payment`, `identity`. Фронтенд обращается к ним через **единый HTTP-шлюз**, не подключается к PostgreSQL, Redis или Kafka и не использует внутренние API.

**Оплата тестовая.** Реального эквайринга, фискализации, интеграции с 1С и контроля прохода нет. Отдельной регистрации посетителей и входа по SMS тоже нет: заказ оформляется по имени и телефону, доступ к нему выдаётся по секретному токену.

## 3. Локальный запуск

Потребуются Docker с Compose v2.24+ и Python 3. Рекомендуется выделить Docker не менее 4 ГБ памяти. Устанавливать Go и базы данных на хост для контейнерного запуска не нужно.

Из корня репозитория:

```bash
cd backend
python3 scripts/init-env.py
```

Скрипт создаст локальный `.env` со случайными паролями и ключами. Если файл уже существует, он не будет перезаписан.

Перед запуском указать в `backend/.env` точный origin локального фронтенда, например для dev-сервера на порту 5173:

```dotenv
ALLOWED_ORIGIN=http://localhost:5173
PUBLIC_URL=http://localhost:8080
COOKIE_SECURE=false
```

Затем выполнить из `backend/`:

```bash
docker compose build catalog booking payment identity
docker compose up -d --no-build --wait
```

Миграции и начальная инициализация выполняются автоматически. Контейнеры миграций и `kafka-init` со статусом `Exited (0)` после выполнения — нормальное состояние.

Проверить доступность:

```bash
curl http://localhost:8080/healthz
curl http://localhost:8080/api/v1/baths
```

`healthz` проверяет шлюз; запрос каталога дополнительно проверяет прохождение запроса к приложению. При проблемах:

```bash
docker compose ps -a
docker compose logs --tail=100 catalog booking payment identity gateway
```

Повторный запуск готовых образов — `docker compose up -d --no-build --wait`, остановка — `docker compose stop`. Данные сохраняются в томах. `docker compose down -v` удаляет данные, для обычного перезапуска эта команда не нужна.

После изменения `.env` повторить `docker compose up -d --no-build --wait`: простой `restart` не обновляет окружение контейнеров. После изменения Go-кода также нужна пересборка образов.

## 4. Подключение фронтенда и CORS

В конфигурации фронтенда задать адрес API, например:

```dotenv
VITE_API_BASE_URL=http://localhost:8080/api/v1
```

Это пример имени переменной для Vite; в другом стеке использовать соответствующую публичную настройку.

`ALLOWED_ORIGIN` принимает один origin со схемой и портом, без пути и завершающего `/`. `http://localhost:5173` и `http://127.0.0.1:5173` — разные origin. По умолчанию разрешён `http://localhost:8080`, поэтому для отдельного dev-сервера настройку нужно поменять.

JSON-запросы отправлять с `Content-Type: application/json`. При cookie-аутентификации добавлять `credentials: 'include'`. В публичные переменные сборки фронтенда нельзя копировать backend `.env`, ключи сервисов или пароли БД.

## 5. Основные группы API

Все пути ниже указаны относительно `/api/v1`. Полные параметры и методы изменения объектов смотреть в Swagger.

| Задача | Основные запросы |
| --- | --- |
| Каталог | `GET /baths`, `GET /baths/{bathID}/departments`, `GET /departments/{departmentID}` |
| Схема и правила | `GET /departments/{departmentID}/resources`, `GET /departments/{departmentID}/booking-config` |
| Свободные варианты | `GET /departments/{departmentID}/availability`, `GET /departments/{departmentID}/availability-calendar` |
| Предварительная цена | `POST /quotes` |
| Черновик | `POST /orders`, `GET /orders/{orderID}`, `PATCH /orders/{orderID}` |
| Удержание и освобождение | `POST /orders/{orderID}/hold`, `POST /orders/{orderID}/release` |
| Тестовая оплата | `POST /orders/{orderID}/payments`, `GET /orders/{orderID}/payments/{paymentID}` |
| Билет | `GET /tickets/{token}`, `GET /tickets/{token}/pdf` |
| Вход сотрудника | `POST /admin/sessions`, `GET /admin/me` |
| Администрирование | Группы `/admin/baths`, `/admin/departments/...`, `/admin/orders`, `/admin/employees` |

Справочные отделения не предлагают онлайн-продажу. Формат отделения и правила из API определяют доступный интерфейс: выбор мест на сеанс или выбор времени аренды сауны.

## 6. Сценарий оформления на фронтенде

1. Загрузить каталог, конфигурацию бронирования и ресурсы выбранного отделения. Схемы используют координаты в диапазоне 0–1000; отображаемый номер места отличается от его внутреннего идентификатора.
2. Запросить доступность и дать выбрать места одного сеанса либо одну сауну на интервал. Доступность может измениться до удержания — нужно обрабатывать конфликт.
3. Отправить выбор и состав гостей в `POST /quotes`. Сервер возвращает предварительную стоимость; ресурсы ещё не удержаны.
4. Создать заказ через `POST /orders` с `selection` и `buyer`. Сохранить `order.id` и `order_token` из ответа. Для защищённых запросов этого заказа передавать `Authorization: Bearer <order_token>`.
5. Выполнить `POST /orders/{orderID}/hold` с телом `{}`. Ответ содержит `order` и `price_changed`; показать актуальную сумму. Таймер рассчитывать по `expires_at` и `server_time` сервера, а не как новые 10 минут при каждом открытии страницы.
6. Создать платёжную попытку с актуальными `amount_kopecks`, `currency`, `price_hash` и тестовым `outcome`: `success` или `declined`.
7. При `202`/`pending` опрашивать состояние попытки и заказа с задержкой между запросами. Останавливать опрос после конечного результата или ухода с экрана; не считать сам факт создания попытки подтверждением посещения.
8. После статуса заказа `confirmed` показать `ticket_url` и возможность получения PDF. Ссылку использовать из ответа API.

Статусы заказа: `draft`, `held`, `confirmed`, `released`, `expired`. Редактирование выбора и контактов доступно в черновике. Отказ оплаты не продлевает удержание; повторная попытка возможна только до исходного срока. Для возврата к новому выбору освободить неоплаченный резерв. Закрытие вкладки не освобождает его мгновенно.

Все суммы — **целые копейки RUB**. Временные метки — RFC3339 с часовым поясом, бизнес-календарь — `Asia/Yekaterinburg`. Цены, возрастные правила, доступные даты, шаги времени и вместимость не дублировать константами во фронтенде: использовать ответы API. Максимум 10 гостей сауны в тестовых данных — неподтверждённое допущение.

## 7. Авторизация сотрудников

Учётные данные первоначального сотрудника находятся в локальном `backend/.env`: `ADMIN_USERNAME` и `ADMIN_PASSWORD`. Пароль создаётся при инициализации БД; изменение переменной при существующей записи не меняет пароль сотрудника.

`POST /admin/sessions` принимает `username` и `password`. Ответ содержит `access_token`, `csrf_token`, `expires_at`; также устанавливается HttpOnly cookie `admin_session`.

- **Cookie:** отправлять `credentials: 'include'`; для изменяющих запросов добавлять `X-CSRF-Token` из ответа входа.
- **Bearer:** передавать `Authorization: Bearer <access_token>`. Для Swagger использовать кнопку Authorize и схему `adminBearer`.

Сессия действует восемь часов. При истечении требуется повторный вход; отдельного refresh-token сценария нет. Выход — `DELETE /admin/sessions/current`.

Роль `admin` управляет операционными функциями, `owner` дополнительно управляет сотрудниками. Права проверяются сервером. Токен сотрудника и токен заказа имеют разное назначение; в HTTP-клиенте выбирать их по типу запроса, не подставлять один общий Bearer во все вызовы.

Токены и билетные ссылки не отправлять в аналитику и логи. Потерянная ссылка на заказ не восстанавливается через публичный поиск по телефону.

## 8. Повтор запросов и ошибки

Для операций, требующих идемпотентности по Swagger, отправлять `X-Idempotency-Key` со случайным UUID v4, например `crypto.randomUUID()`.

- Новое действие — новый ключ.
- Повтор того же действия после сетевой ошибки — прежний ключ и то же тело. Ключ сохранить до отправки, особенно при создании заказа.
- Изменённое тело с прежним ключом вызывает конфликт.
- Повтор может вернуть сохранённый ответ операции; актуальное состояние получать через `GET`.
- При изменении объектов передавать версию, указанную контрактом. После конфликта перечитать объект, а не перезаписывать изменения вслепую.

Ошибки имеют формат:

```json
{
  "error": {
    "code": "machine_readable_code",
    "message": "Описание ошибки"
  }
}
```

Типичные статусы: `400` — некорректный ввод, `401` — отсутствующий или недействительный доступ, `403` — недостаточные права или CSRF, `409` — конфликт состояния, `429` — превышение лимита, `503` — временная недоступность. Точные коды и условия смотреть у конкретной операции в OpenAPI. Не повторять изменяющие запросы бесконечно.

### Подсветка конфликтующих мест

Если `POST /orders/{orderID}/hold` возвращает `409` с кодом `resource_unavailable`, ответ содержит полный список недоступных ресурсов из текущего выбора:

```json
{
  "error": {
    "code": "resource_unavailable",
    "message": "Часть выбора недоступна; ни один ресурс не удержан",
    "details": {
      "resource_ids": ["resource-id-1", "resource-id-3"]
    }
  }
}
```

Сопоставить эти значения с `id` ресурсов на схеме и подсветить их как недоступные. Это внутренние идентификаторы, а не отображаемые номера мест. В список входят выбранные ресурсы, занятые удержанием, подтверждённым заказом или административной блокировкой; свободные места не включаются. Ответ не раскрывает чужие заказы или контакты.

Частично удержанных мест нет: весь выбор остаётся не зарезервированным. Заказ остаётся черновиком, который можно изменить через `PATCH /orders/{orderID}`, а затем повторить удержание с новым ключом операции. При необходимости перечитать `availability`: список конфликтов отражает момент проверки и не гарантирует дальнейшее состояние схемы. Для других кодов `409` поле `details` может отсутствовать.

## 9. С чего начать интеграцию

Сначала запустить backend, открыть Swagger и получить каталог. Затем подключить публичный сценарий «выбор → цена → черновик → удержание → тестовая оплата → билет», после него — вход сотрудника и административные экраны.

Для демонстрации полного пути из `backend/` можно выполнить `python3 scripts/demo.py`. Скрипт создаёт настоящий локальный тестовый заказ и сохраняет результат в `tmp/demo-result.json`; файл содержит секретные данные доступа, его не следует коммитить или пересылать.
